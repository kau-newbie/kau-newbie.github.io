# Spring 프로젝트 - 홈캠 서버 구현하기

프로젝트를 진행해볼겸, Spring으로 서버를 구현하기로 했다. 그 전에, Spring 공부한 내용을 정리하려고 한다.

## Spring이란

**Spring**은 **framework**이다.

### framework란?

프레임워크는 [위키피디아](https://ko.wikipedia.org/wiki/%EC%86%8C%ED%94%84%ED%8A%B8%EC%9B%A8%EC%96%B4_%ED%94%84%EB%A0%88%EC%9E%84%EC%9B%8C%ED%81%AC)에서 정의하기를,

<blockquote style="padding: 10px 15px; border-left: 4px solid #cbcbcb; background-color: #f9f9f9; color: #555;">
"소프트웨어 프레임워크(software framework)는 개발자가 완전한 솔루션을 만들기 위해 확장하거나 맞춤화할 수 있는 재사용 가능하고 일반적인 기능을 제공하는 소프트웨어다. 간단히 뼈대, 골조(骨組), 프레임워크(framework)라고도 한다.(생략)"
</blockquote><br>

위의 정의를 대강 살펴보면, "재사용 가능하고 일반적인"이란 말이 들어있다. 개발자들이 사용하기 편한 수준으로 (시스템레벨, 네트워크 설정, DI 처럼 세세하게 신경써야하는 코드를 다 짜놓아서) 자주 쓸만한 기능들을 제공한다는 말이다.(*추상화*라고 하겠다.)
> 이 기능들을 사용하는 방법은 보통 메서드 호출이 있고,
>
> 보통은 이 메서드 호출마저 '프레임워크가 자동으로 해주도록' *어노테이션(@)*을 이용한다.

  <li>프레임워크(Framework): 내가 그 안에 들어가서 규칙을 따라야 하는 틀이자 '프로그램의 뼈대'.</li>

계속해서 젬나이의 말을 각색하자면, Spring이 framework인 이유는 2가지가 있다고 한다.

1. **제어의 역전(IoC)**
  **IoC(Inversion of Control)**이란, 내가 코드를 짜고 시스템의 실행 흐름을 주도하며, 그 사이사이에 여러 라이브러리들의 메소드 등을 호출하는 방식이 아니라, Spring이라는 프레임워크가 전체적인 실행흐름을 주도해서, 개발자는 그 사이의 작은 실행흐름들에만 집중하도록 하는 방식을 말한다.
2. **프레임워크(뼈대, 시스템의 구조)를 제공**
  반복적인 작업을 줄일 수 있는 기능들을 제공한다. 이를테면 Spring은 내장된 톰캣을 실행하고, DB 커넥션을 연결하고, 미리 사용자가 만들어서 등록해놓은, 혹은 사용하기로 한 객체들을 만들어놓고, 자동으로 DI 및 생명주기를 관리한다. DB 조회 중 에러가 나면 다시 롤백을 하는 기능도 들어있다.

말을 좀 바꿔서 미안하지만, 사실 Spring은 엄밀히 말하면 생태계라고 표현하는 게 맞는 것 같다.

Spring이라는 기술 표준에 맞추어 다양한 기능을 제공하는 모듈이 있다.([이 사이트에서 확인할 수 있다.](https://spring.io/projects))

사이트를 들어가보면 알겠지만, 여러 모듈 중에는 Spring Security(보안 기능 모아놓은 모듈), Spring Boot(Spring framework 쓰기 편하게 기본 설정들을 자동화해놓은 Spring 기반 응용 프로그램), 그리고 Spring Framework 등이 있다.

### Spring Framework

Spring Framework라고 아예 이름이 붙은 이 모듈은 말 그대로 Spring 기반 Framework에서 핵심 기능들을 담당하고 있다.
- **Core technologies**: dependency injection, events, resources, i18n, validation, data binding, type conversion, SpEL, AOP.
- Testing: mock objects, TestContext framework, Spring MVC Test, WebTestClient.
- Data Access: transactions, DAO support, JDBC, ORM, Marshalling XML.
- **Spring MVC** and Spring WebFlux web frameworks.
- Integration: remoting, JMS, JCA, JMX, email, tasks, scheduling, cache and observability.
- Languages: Kotlin, Groovy, dynamic languages.

공식 문서에서 이런식으로 설명이 나와있다. 앞서 언급했던 DI이외에도 data binding 등 다양한 기능이 들어있다. 그리고 Spring MVC는  Spring의 Model-View-Controll을 포함한 기본적인 웹 어플리케이션 아키텍처에 대해 지원하는 기능들이 들어있다.
> 가령, @Controller라고 annotantion을 단 클래스는 컨트롤러로서 동작하며, 
> 1. 컨트롤러 안 각 메서드 위 @GetMapping(), @PostMapping()등의 annotation에 써놓은 주소로 http 요청이 오면, 
> 2. 해당 메서드를 프레임워크가 알아서 호출해주는 식이다.

프로젝트에 들어가기에 앞서 설명이 자꾸 길어지지만, 좋은 게 좋은거니까. 이번에는 Spring Framework의 전체적인 동작을 살펴보려 한다.
- 최대한 annotation 사용과 연관지어 알아보겠다.

## Spring의 기본 동작

물론 그 전에, annotation에서 자주 본 @Model, @Controller도 그렇고, 위에 언급된 Spring MVC에서 이 **MVC**라는 개념을 알고 들어가야겠다.

#### MVC

**MVC**라는, 설계 패턴 중 하나를 소개한다.

Spring MVC 또한 이 패턴을 편리하게 지원하기 위해 만들었다. 오늘날, 서버가 페이지를 랜더링하지 않고 프론트엔드 단에 데이터만을 넘겨주는 역할을 한다지만, 여전히 MVC의 기능들은 필수 요소이고, 많이 쓰인다.

MVC는 다음과 같이 이루어져있다.
- Model
- View
- Controller

**Controller**는 사용자 요청에 대해 올바른 동작을 호출하는 역할을 하는 레이어(layer)이다. 
- 가령, "/user/login" GET 요청에는 login 페이지를, "/user/login" POST 요청에는 DB를 조회 등, 해당 비즈니스 로직을 담당하는 Service의 특정 메서드를 호출하는 식이다. 
> 해당 메서드에는 처음 서비스 호출부터, 그 결과에 따른 redicreting(페이지 이동) 등을 포함한다.

**View**는 사용자에 보여줄 화면을 주로 '템플릿'이라 부르는 틀로서 만들어 놓고, 후에 DB에서 model을 통해 받아올 데이터로 채워놓아 완성한다.

  예를 들어, 

  ```java
   
   <div>환영합니다, <span th:text="${usrId}">unknown</span>님.</div>

  ```

  이런식으로 html 문서 안에 **thymeleaf**라는 Server-Side 템플릿 엔진을 통해 템플릿을 구성한 뒤, 저 {usrId} 부분을 Controller에서 

  ```java
  model.addAttribute("isLoggedIn", false);
  model.addAttribute("usrId", "Guest");
  ```
  과 같이 model이라는 Model 객체에 attribute를 담아두어 채우게 된다. 그 후 다시 이 thymeleaf에서 Model을 통해 받아와 채워준다.


**model**은 데이터를 담아두는 일종의 보관소, 이 보관소에서 데이터를 주고 받는 로직, DB와의 연결을 통해 데이터를 저장/불러오는 로직 등 모든 것을 아우르는 레이어이다. 

```

===============================================================
[ MODEL LAYER (비즈니스 로직 + 데이터) ]
---------------------------------------------------------------
1. 데이터 저장소 접근 : Repository (DAO)
2. 비즈니스 상태/구조 : Entity / Domain Object
3. 데이터 이동 바구니 : DTO (Data Transfer Object)
4. 핵심 비즈니스 로직 : Service (Service Layer)
===============================================================

```

위에 나왔듯, 일종의 데이터 보관소로서 Model Interface 구현체를 사용할 수도 있고,

> 이때, dto와 entity라는 두 개의 닮은? 개념이 나온다.
> - **DTO**(Data Transfer Object): 순수하게 계층(layer)간 데이터를 주고 받을 때 사용할 '데이터 틀'이다. 
>   - 이를테면, Entity에서 필요 없는 정보들을 빼서 어떤 하나의 DTO로 정해놓으면, 담겨있는 데이터들은 미리 정해놓은 형태, 종류로만 구성된다. 안전하다고 볼 수 있다! 정해놓은 데이터들만 담을 수/수정할 수 있기 떄문이다.
> - **Entity**: DB의 특정 table과 1:1 대응 관계가 되는 객체이다. JPA가 이 Entity를 통해 DB를 조작하게 된다. 
>
> 더 자세한 건 이따 마저 적기로 하겠다.

사용자로부터 버그 리포트 게시판 페이지 요청을 받은 후, 해당 페이지를 보내는 과정은 아래와 같다.

#### 예시그림 {#example-schema1}

```text

[ 클라이언트 (브라우저) ]
       │  ▲
(1) @Controller / @RestController  <-- 화면을 주거나 JSON/XML API 응답을 주는 관문
       │  ▲
(2) @Service                       <-- 핵심 비즈니스 로직 (로그인 검증, 데이터 가공 등)
       │  ▲
(3) @Repository                    <-- DB 테이블과 통신하여 데이터를 가져오고 저장함 (DAO/JPA)
       │  ▲
[ 데이터베이스 (DB) ]

```

(젬나이보고 그려달라고 했다.) DB에서 사용자 요청에 대한 데이터를 가져오기까지 Controller, Service, Repository라는 *컴포넌트*(`기능단위`라고 할 수 있을 것 같다.)들을 거친다. 

이 컴포넌트들은 모두 스프링이 관리하는 **Bean**(Spring이 관리하는 객체)이 되며, 각각의 특화된 역할을 수행한다고 한다. 

젬나이의 정리를 복붙해두겠다. 대충 읽어두고 밑에 부분을 마저 읽다가, 필요할 때 돌아와서 보면 되겠다.

1. **기본적인 annotation들**

    스프링 컨테이너에 "나를 빈으로 올려줘!"라고 말하는 가장 기본적인 컴포넌트 종류들입니다.

    `@Component`: 가장 기본적이고 범용적인 스프링 빈 등록 애너테이션입니다. (아래의 컨트롤러, 서비스, 리포지토리는 모두 이 @Component를 확장한 특수 형태입니다.)

    `@Controller`:

    역할: 사용자의 요청(HTTP Request)을 받아 HTML 화면(Thymeleaf 뷰 등)을 반환하는 프레젠테이션 레이어의 수문장입니다.

    안드로이드의 Activity처럼 사용자와 직접 맞닿아 화면을 제어하는 진입점 역할을 합니다.

    `@Service`:

    역할: 실질적인 핵심 비즈니스 로직(예: 사용자가 입력한 비밀번호가 일치하는지, 결제 승인이 가능한지 등)을 수행하는 비즈니스 레이어입니다.

    화면이나 DB 기술에 종속되지 않는 순수한 프로그램의 핵심 규칙이 여기에 담깁니다.

    `@Repository`:

    역할: 데이터베이스나 파일 등 영구 저장소(Persistence)에 접근하여 데이터를 쓰고 읽는 데이터 액세스 레이어입니다.

    안드로이드의 로컬 DB인 Room Database DAO와 정확히 같은 역할을 합니다.

2. **웹 요청 매핑 애너테이션 (Controller 내부에서 사용)**

    사용자가 보낸 URL 주소에 따라 어떤 메서드가 실행될지 교통정리를 해주는 애너테이션들입니다.

   `@RequestMapping`: 특정 URL 경로를 컨트롤러 클래스나 메서드에 매핑합니다.

    `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping`:

    각각 HTTP GET(조회), POST(등록/로그인), PUT(수정), DELETE(삭제) 요청이 들어왔을 때 실행될 메서드를 지정합니다.

    예: 우리가 작성할 로그인 요청 폼에서 POST 방식으로 보낸 데이터는 @PostMapping("/login")이 붙은 메서드가 가로채서 처리합니다.

3. **데이터 및 자바 설정 관련 애너테이션**
  
    `@Configuration`: 해당 클래스가 스프링의 설정을 위한 자바 클래스임을 선언합니다. 내부에서 @Bean을 사용해 외부 라이브러리 객체들을 빈으로 등록합니다.
  
    `@Bean`: 개발자가 직접 제어할 수 없는 외부 라이브러리(예: BCryptPasswordEncoder)를 스프링 빈으로 등록할 때 메서드 위에 붙입니다.

기본적인 컴포넌트들(model, controller, service 등) 이외에 외부 라이브러리나 직접 만든 클래스들도 Spring이 관리하도록 하기 위해서 @Configuration, @Bean을 사용하는 경우를 주의깊게 찾아보면 도움이 될 것이다.

이제 annotation의 실제 사용 예시를 들어보겠다.

### annotation 사용 예시

실제 코드들을 넣어가며 위에서 나온 [그림(schema)](#example-schema1)을 설명해보겠다.

#### 1. 사용자 요청

  처음에 사용자는 `home.html`이란 홈페이지에 위치해 있다. 이제 아래와 같은 코드로 인해, 버튼을 눌러 서버로 해당 페이지 요청을 보내게 된다.

  ```html

  <a sec:authorize="hasRole('ADMIN')" th:href="@{/admin/bug-report/list}" class="btn btn-outline-secondary" role="button">⚙️ bug report list</a>

  ```

  대충 읽어보면 \<a> 레이블(<>로 감싼 하나하나가 레이블이라 부르는 단위이다.)이 `role="button"`이기 때문에 버튼 역할을 한다. 특히  `th:href="@{/admin/bug-report/list}"` 부분에 의해 이 버튼을 눌렀을 때 해당 경로로 http GET요청을 서버에 보내게 된다.
  - '경로'는 실제 톰캣에서 웹app을 만들던지, Spring Boot에서 만들던지, 어플리케이션 자체(/) 아래의 디렉토리 구조(폴더 구조)를 따른다.
  > 예를 들어, 'my-webapp'이라는 웹앱이 있으면, 그 아래 Spring Boot로 src/main/resource/template 경로 아래에 home.html을 만든다.
  > 
  > 이제 `href="/home"`요청은 my-webapp 아래 home.html로 갈 것이다. 
  > - 물론 Controller에서 어떤 경로던지 다른 동작을 할 수 있게끔 바꿀 수 있다.
  - `<a href="/admin/bug-report/list">`와 같은 의미로, href의 default는 항상 GET요청이다.
    - `th`는 `thymeleaf`라는 도구를 사용한다는 뜻이다. 주로 Spring MVC와 호환성도 좋고, html 태그에 그대로 사용할 수 있는 장점이 있따.
  > 왜 굳이 th:href를 사용했냐 하면, 
  >
  > thymeleaf를 쓰면 기본적으로 *?id=10&page=2*처럼 뒤에 붙을 동적인 파라미터도 알아서 작성해주고, 
  >
  > 보통의 url과 달리, Context Path(여기선 'my-webapp'을 적어줘야하는 경우: "/my-webapp/home")를 적어줘야 하는 경우가 있는데, 이럴 경우 이 Context Path를 자동으로 적어준다고 한다.
  - 서버에서는 @Controller에서 ("/admin/bug-report/list")에 대해 mapping(특정 메서드가 호출되도록 연결)해줄 수 있다.

  정리하자면, 사용자는 */admin/bug-report/list* 경로로 `http get` 요청을 서버에 보낸다.

#### 2. 이제 Spring Framework의 차례

  Spring Boot를 통해 미리 톰캣도 돌리고, 설정해놓은 Bean들도 미리 만들어두고(DI대기), 대기 중이다가 사용자 요청이 들어오면 해당 요청을 Controller에게 넘겨준다.

  ```java
  @Controller

  public class BugReportController {
  ```

  다른 것보다 아까 버그리포트 게시글은 */admin/bug-report/list* 경로로 요청을 보내도록 했다. 해당 경로에 대한 메서드를 찾아보면,

  ```java

  // 1. 관리자가 버그 리포트 조회 버튼을 눌렀을 때
  	@GetMapping("/admin/bug-report/list")

  	    model.addAttribute("reports", reports);
  ```

  요 부분이다. `PreAuthorize`는 메서드 실행전에 authorize(권한)을 확인하라는 뜻인데, 이건 Spring Security가 다루는 내용이라 여기선 더 자세한 내용은 생략한다. 아무튼 이 메서드 위에 `@GetMapping` annotation이 붙어있는 것을 확인할 수 있다.

  이제 Spring Framework는 (정확히는 Spring MVC이다.) 사용자의 요청에 대해 컨트롤러 안 해당 메서드를 실행할 것이다.
  > 이때, 인자로 넘어가는 `Model`이란 게 있다. 위에서 언급했듯, Interface의 구현체로, Spring에서 별도로 제공하는 기능이다. 
  > - Spring MVC에서 자동으로 model 변수에 담아준다.

  첫 줄에서는 바로 `BugReport`라는, 사전에 내가 만들어둔 **Entity**의 List를 `bugReportService`라는 **Service**의 특정 메서드로 받아온다.

  아까 봤던 [MODEL 그림](#example-dataflow1)에서 보면, 이 *Service*안에서 *Repository*에 의해 DB로부터 데이터를 가져오고, 다시 Controller에서 DTO로 변경되거나, 혹은 바로 사용될 것이다. 
  - 반대로도 가능하다. *DTO*에 맞게 받은 데이터를 *Entity*로 변환하고, 다시 이 Entity가 *Repository*에 의해 DB에 저장될 것이다. 

  Service를 살펴보자.

  ```java

  @Service
  @RequiredArgsConstructor
  public class BugReportService {

      // 일부 생략...
      private final BugReportRepository bugReportRepository;

      // 1. 모든 버그 리포트 목록 가져오기
      @Transactional(readOnly = true)
      public List<BugReport> findAllReports() {
          // Iterable로 나오는 결과를 List로 변환하여 반환합니다.
          List<BugReport> reports = new ArrayList<>();
          bugReportRepository.findAll().forEach(reports::add);
          /**
           *  for (BugReport bug : bugReportRepository.findAll()) {
     				    reports.add(bug);
  			      } 과
  			      bugReportRepository.findAll().forEach(bug -> reports.add(bug)); 는 동일한 코드.
           */
          return reports;
      }
  }

  ```

  역시나 `@Service` annotation으로 Service 컴포넌트로 등록해놓았다. 그리고 `@RequiredArgsConstructor`라는 특이한 annotation도 보인다.

  `@RequiredArgsConstructor`는 **Lombok**이란 아주 유용한 자바 라이브러리에서 제공하는 기능이다.
  > 롬복에서는, Getter, Setter, 생성자(Constructor) 등을 annotation 한 줄로 적어두면, 알아서 컴파일시 생성해준다.
